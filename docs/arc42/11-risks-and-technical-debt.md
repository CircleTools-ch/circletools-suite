# 11. Risks and Technical Debt

> Living register. Add risks as they emerge; link mitigations to ADRs or backlog items.

## 11.1 Risks

| # | Risk | Impact | Likelihood | Mitigation |
|---|------|--------|-----------|------------|
| R1 | Sync/conflict complexity underestimated | High | Medium | Decide strategy early (sync ADR); start with simple last-write-wins per aggregate + escalation hook |
| R2 | Blazor render model choice hurts offline/first-load | Medium | Medium | Prototype WASM-PWA vs Auto before committing (render-model ADR) |
| R3 | Passkey/WebAuthn cross-platform effort | Medium | Medium | Spike per platform; isolate behind `CircleTools.Identity` |
| R4 | MAUI + strict analyzers/warnings-as-errors friction | Low | Medium | Scoped `NoWarn` for generated/MAUI code in `.editorconfig` |
| R5 | Scope creep (many apps too soon) | Medium | Medium | Roadmap discipline; ship Secret-Santa MVP first |
| R6 | **iOS updates acquire an expiry date if no Apple-silicon Mac is bought.** .NET 10 needs Xcode 26, which needs macOS 26 — which only two Intel MacBook Pro models run at all, and macOS 27 (autumn 2026) drops Intel entirely. Apple's next spring SDK deadline then blocks every iOS update, including security fixes | High | High if deferred | Buy the build host ([ADR-0031](../adr/0031-ios-build-host.md)); until then treat any Intel Mac as a single-release bridge, not a plan |
| R7 | **Store account lock-out.** Publishing rights rest on one Apple ID and one Google account; losing 2FA access to either stops all updates for that platform, with no fast remedy | High | Low | Dedicated project accounts, password manager, **recovery codes stored offline** ([ADR-0030](../adr/0030-mobile-store-publisher-identity.md)) |
| R8 | **Permanent identifiers chosen before the brand is.** Bundle id / `ApplicationId` cannot change after the first release, and passkey RP-IDs do not migrate — a placeholder shipped once is shipped forever | High | Low | ✅ **Resolved 2026-08-13** — brand + domain chosen (`circletools.ch`); bundle id **set** to `ch.circletools.secretsanta`. RP-ID/origin will be `circletools.ch`, applied at deployment ([naming](../process/naming.md), [NFR-007](../requirements/non-functional/NFR-007-store-distributability.md)) |
| R9 | **An authorization bug in Circles leaks a family's data to a stranger**, not a user's data to themselves. Circles is the first data in the suite that belongs to *other people*, so the failure mode of a missing check changes character — and a missing check is invisible to every functional test that only calls an endpoint as its owner | High | Low | Enforcement is structural, not reviewed: `CircleRoleFilter` on every circle-naming route, the role required as endpoint **metadata** so `CircleEndpointGuardTests` fails the build when a route is added without a guard, and a 71-row matrix over 14 routes × 5 caller kinds. M2's close is the argument for it — the metadata had been built to be read back and nothing read it ([NFR-006](../requirements/non-functional/NFR-006-circle-authorization.md), [TP-003](../features/TP-003-m2-circles.md)) |
| R10 | **Enumeration resistance decays as surfaces are added.** Every new endpoint accepting an email address is a new place where the branch with less work to do answers sooner. Four surfaces already needed `RequireConstantTime`, and one of them sat at a steady 1.9× for the whole of M1 beneath a 3 ms noise floor that hid it | Medium | **High as the suite grows** | Paired body/status/timing tests per surface, and a documented rule for when a new endpoint needs the filter ([NFR-005](../requirements/non-functional/NFR-005-account-enumeration-resistance.md)). The reliable signal is a **stable ratio across differently loaded runs** — noise does not hold a ratio |

## 11.2 Technical debt

| # | Debt | Planned resolution |
|---|------|--------------------|
| D1 | API-reference section empty until code exists | ✅ Resolved 2026-07-28 — the `src/` projects exist and the reference generates from their XML doc comments |
| D2 | Guideline documents are outlines | Fleshed out as the relevant code is written |
| D3 | Placeholder brand name `Suite`/`<Suite>` | ✅ Resolved 2026-07-24 — finalized as **CircleTools**; token replaced repo-wide |
| D4 | **The WebAuthn ceremony is not automated.** Every passkey test is negative or an authorization check — none creates a credential, because an in-process `WebApplicationFactory` has no authenticator. The ceremony was verified by hand through a CDP virtual authenticator, but nothing re-checks it, and **NFR-004's "no private key, no biometric data" has no stored credential to inspect** | ✅ **Resolved 2026-08-18** — a browser-driving E2E host ([ADR-0045](../adr/0045-browser-driving-e2e-test-host.md)): `tests/E2E/CircleTools.WebAuthn.E2E.Test` drives Chromium with a **CDP virtual authenticator** against the AppHost-launched stack, registering a real passkey (FR-010) and signing in with it (FR-011), then reading the stored credential back as public-metadata-only (NFR-004). Runs as a dedicated gating `webauthn-e2e` CI job. This is the host **D8** now reuses. Closes [TP-002](../features/TP-002-m1-identity.md) gap 4 |
| D5 | **No CI pipeline.** The suite is green only on whoever last ran it locally, so the Definition of Done's "CI green" cannot be met by any milestone | ✅ **Resolved 2026-08-13** — GitHub Actions gate ([ADR-0038](../adr/0038-ci-cd-pipeline.md)): `build-test` (non-MAUI solution + full test run), `docs` (link-checked DocFX) and `build-maui` (Android + Windows heads) on every push/PR to `main`. CD to the VPS is deferred to milestone 8 |
| D6 | **M1 and M2 are built but cannot ship.** The transactional-email provider (FR-007/009/013, and now FR-017's invitations, all depend on delivery) and the hosting/suite domain (passkey RP-ID, the CSP origin, the NFR-004 residency target) are both undecided. M2 **sharpens the first**: an invitation is the only mail the suite sends to somebody with no relationship to it, so deliverability, unsubscribe expectations and abuse reporting stop being account concerns and become onboarding concerns | Deployment ADRs — the strategy for each is settled, only the provider and the literal domain are missing ([naming](../process/naming.md)) |
| D8 | **The sign-up-from-an-invitation-link journey is not automated end to end.** Both halves are covered (M1's register → verify → sign in, and M2's accept), but nothing drives a mail link through sign-up in one test — the join is walked in a browser instead. It is the largest hole in M2's own coverage | ✅ **Resolved 2026-08-19** — `InvitationSignUpTests` in `tests/E2E/CircleTools.WebAuthn.E2E.Test` drives the whole journey in one Chromium session on the D4 browser-driving host ([ADR-0045](../adr/0045-browser-driving-e2e-test-host.md)): an admin invites an address with no account (set up over the API), and the recipient follows the invitation mail link to the anonymous landing, creates an account, verifies it, signs in and joins (FR-018) — membership asserted server-side, and the invited address never surfaces in the people list (NFR-006). Runs in the gating `webauthn-e2e` CI job. Closes [TP-003](../features/TP-003-m2-circles.md) gap 7 |
| D9 | **Two M2 acceptance criteria wait on M4.** FR-019's *"a managed member copied into a Secret-Santa group is unaffected by their removal from the circle"* and FR-022's *"a group created from a deleted circle opens unchanged"* have nothing to act on: no code copies a circle into a group yet. The rules are stated in the model and unverifiable | M4 — create a group from a circle. Recorded here rather than left as ticked rows in TP-003 |
| D7 | **The MAUI head still carries template art.** `ApplicationId` is now set to the final `ch.circletools.secretsanta` (2026-08-13), but the icon and splash are still the .NET template art (`#512BD4`) and `RevealBaseUrl` still points at `localhost:7081` | Icon/splash: replace before first submission. `RevealBaseUrl`: set to the production origin at the deployment milestone ([naming](../process/naming.md), [ADR-0030](../adr/0030-mobile-store-publisher-identity.md)) |
